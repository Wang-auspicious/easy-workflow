# 自主建线与业务线接通

本轮在 v0.2.0 与 Claude 第二轮界面之上实现。默认内核仍为 v1；没有迁移用户项目。

## 主调度现在能做什么

直接告诉主调度目标，例如：“创建一条文本分析线，标准化后并行统计和提取关键词，汇总为 JSON；先试跑再处理这些文本。”主调度可以自己完成建线、修正、试跑、启用和正式投料，不需要用户手工编辑清单。

| 能力 | 实际行为 |
|---|---|
| `workflow_authoring` | 读取完整模板源码、已有程序、可用工位工具及角色编写契约 |
| `workflow_draft` | 保存清单、角色文件、输入/输出 schema；返回编译错误。更新需匹配 `expectedRevision` |
| `workflow_edit` | 按 JSON Pointer 原子增量修改节点、边、映射、schema 和角色；匹配版本后重新完整校验，失败不留下半份修改 |
| `workflow_drafts` | 列表、完整草稿、最近 20 份试跑摘要；传 `trialId` 可读完整回执 |
| `workflow_trial` | 在独立目录运行真实程序和已配置模型，检查样本输出与状态，记录未覆盖工位和产物 SHA-256 |
| `workflow_activate` | 核对同一草稿版本、当前内核、通过回执与产物摘要，在空闲项目启用；重复请求返回已有结果 |
| `workflow_feed` | 按入口 schema 验证正式输入并运行；不能绕过已有上游与审查工位 |
| `workflow_result` | 有界等待指定任务，读取真实 JSON 文件，核对归属、字节数和 SHA-256；仅状态与文件都通过时返回 `readyForDelivery: true` |

支持串行、并行汇合、条件分支、审查退回、跨线信道和人工分支。每个岗位都有实际执行器和 ROLE.md。主调度还可以修订自己创建的工作流，旧版本保留；既有内置线与用户安装包的改动继续使用原有用户决策入口。

自动建线使用宿主内置程序及 Agent 能力箱。新增宿主代码、外部 CLI/MCP 命令和凭据仍使用用户安装入口；模型不能把草稿文本变成直接执行的宿主代码。Agent 继承项目模型与适配器配置。

纯字段汇合可使用 `compose-json`：按输入映射原样复制已完成分支的数据，不再让模型重抄程序统计。审查退回应指向能够修改错误内容的生产者。试跑回执同时提供失败工位及错误、每个断言的预期与实际值；`expect.values` 使用点分字段路径，对象按完整 JSON 值比较。参数契约错误也在模型能看到的消息正文中保留具体字段诊断。

最新真实主调度建线、修订和交付核验见 [自主建线实测记录](workflow-authoring-live.md)。

## 其余六条业务线

`business_lines` 返回当前启用状态、输入契约、真实产物和自动上下游。`business_feed` 在开跑前检查输入，避免空数据进入生产后才失败。

| 线 | 输入与产物 |
|---|---|
| 组件 | 源站、可选同站组件页面、`componentLimit`；保存真实舞台截图与描述，发布后自动续批 |
| 图鉴反哺 | 自动消费已发布组件，按类型汇总；不允许直接投料绕过组件审查 |
| Skill / DESIGN.md | 保存原件字节、出处和许可，生成简介后审查 |
| 科研绘图 | 真实数值或隔离容器复现输入；保存 PNG/PDF、数据和可复现代码 |
| PPT | 完整 PPTX/PDF deck 直接地址；保留原件并渲染每页预览 |
| 图像处理 | 真实原图和明确变换；保存原图、处理结果、参数和限制 |

修复的交接问题：

- 候选分流识别带查询参数的 Skill/PPTX 地址，以及明确的组件、绘图和图像处理输入。普通 PDF 不默认当作 deck。
- v2 信道携带前序工位累积的业务数据；不携带原任务的发布、失败、重试和会话状态。
- v2 组件分页自动续批，使用持久任务标识去重；每批已发布组件自动进入图鉴。
- 空闲的 v2 项目不再因启动暂停选项被误判为正在暂停的轮次。
- 沿用 Claude 界面，仅修正 Skill/PPT 产物文案及组件数量字段。

## 已有验证

- 类型检查与 UI 单元测试 45 项通过。
- 工作流控制、v2 图语义与信道回归 51 项通过。
- 工作流包、HTTP 控制与业务集成回归 56 项通过。业务集成使用真实本地原件、浏览器、Python 和原生 PPTX 渲染；审查回答是 fixture，不能据此声称真实模型的六线业务质量全部验收。
- 补充验证草稿恢复、回执读取、产物篡改拒绝、同版重复启用、修订后的旧回执拒绝及宿主代码拒绝。
- **真实主调度模型验收成功**：使用本机已有的 `cliproxy / gemini-3.8-flash-high` 配置，模型自行调用两次 `workflow_draft`、一次 `workflow_trial`、一次 `workflow_activate` 与一次 `workflow_feed`，创建 `authored-analysis` 并正式发布 1 件文本分析产物。没有模拟主调度回答。
- **真实模型工位试跑成功**：生产 Agent → 独立审查 Agent → 发布程序完整执行；根据给定事实撰写两句话，通过真实模型审查，保存 203 字节 JSON 产物，SHA-256 为 `a172d55608d4349ee97e35e1c634313d2732d2767da11f87845821704f481ba1`。
- 打包版在独立桌面配置中通过原生窗口、浏览器会话、截图、只读保护、重启与后端退出检查。
- 全量回归首轮：786 项，769 通过、16 失败、1 跳过，耗时约 17 分 47 秒。失败由建线服务过早初始化（15 项）和旧 MCP 授权文案断言（1 项）导致；修复后相关控制回归 18/18、MCP 4/4 通过。唯一跳过项在连接规则目录后补验 1/1 通过。没有把首轮记录改写为全绿，也没有重复运行整个长测试套件。
- 最终桌面包 v1、v2 分别 25/25 通过。桌面快捷方式已指向本次本地新包；旧分发目录保留。GitHub 当前发行版仍为 v0.2.0。

真实模型验收可显式运行：

```sh
node scripts/workflow-authoring-smoke.ts
```

该命令使用本机已配置的模型，会产生模型用量；仅创建独立临时项目，保留 `acceptance.json`、日志、草稿、试跑与正式产物。普通 `npm test` 不调用该真实模型脚本。

项目内持久记录位于 `workflow-authoring/drafts/`、`workflow-authoring/trials/`、`workflow-authoring/activated/`；生产安装仍在 `packs/`。通过的有限样本不能证明所有分支与业务质量：试跑会返回未覆盖工位，主调度需按目标补充样本。此前 v2 长运行验收缺口仍以原记录为准。
