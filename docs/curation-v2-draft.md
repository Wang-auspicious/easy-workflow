## 1. 基准为什么质量高

基准流程只有一个前提：**先真的进站读懂，再动手。**工序第 3 步要求，动手前至少打开首页、目录页、一个具体条目页，以及关于 / 定价 / 许可 / 页脚，并回答四个问题：它是谁、能拿走什么、有多大、许可和价格是什么。后面的选页、事实和文案都建立在这份理解上。

当时用的办法是：在真实浏览器里打开页面，用 `get_page_text` 读渲染后的全部可见文字；站点如果有 `llms.txt` / `llms-full.txt` / sitemap，也一并读。

Easy Workflow 现在缺的正是这一步。每个工位只拿到首页的前 1,200–2,500 字和首页上的链接：

- 选页靠给链接文字和路径打分；
- 事实核验最多用正则挑 3 个页；
- 文案员只读首页 1,200 字。

这一轮选页和事实上的问题，几乎都能追到这里。

## 2. 逐站对照

| 环节 | 基准 | Easy Workflow 现在 | 差距 | v2 怎么做 | 谁做 |
|---|---|---|---|---|---|
| 查重 | 域名、产品名、仓库名、npm、旧域名算同一实体 | 按规范 URL 和域名 | 仓库 / npm / 旧域名没归到同一实体 | 候选层规范化时生成实体键（§5） | 程序 |
| 进站读懂 | 浏览器读 4–6 页，回答四问 | 无 | **最大的缺口** | 侦察员建站点卷宗 → 阅读员读懂并出拍摄单（§3） | 程序 + LLM |
| 分类 | 读懂后判断，附证据 URL | 只看首页前 2,000 字 | 证据太少 | 分类员和复核员都读卷宗；复核员不看阅读员和分类员的结论；两人并行 | LLM ×2 |
| 标签（facets 12 轴） | 对照 taxonomy 勾选 | **没有** | 整块缺失 | 编目员从受控词表中选，程序校验取值合法 | LLM + 程序校验 |
| 首屏 / 目录 | 读懂后挑页 | 给链接打分 + 模型从编号里挑 | 只看链接，看不到页面里有什么 | 按阅读员的拍摄单拍；拍摄单失效才退回阅读员 | 程序 |
| 组件特写 | 读懂后挑页，人看过画面 | 盲试最多 6 页，挑像素占比最高的 | 选页和挑舞台都靠像素 | 拍摄单定页面；Agent 看候选舞台缩略图挑主体；程序负责打开、等待、裁切 | LLM + 程序 |
| 截图检查 | 人看三张图 | 像素规则 + 看图审查 | 基本对齐 | 保留，退回时 repair 分三种 | 程序 + LLM |
| 风格 | §2.6.1 五步 | 已按五步实现 | 对齐 | 保留 | LLM + 程序否决 |
| 事实 | 五项最低要求（作者 / 组织 / 仓库 / 许可 / 价格），每项带 sourceUrl + evidence，写明覆盖范围 | 四项（价格 / 源码 / 许可 / 商用），只看首页和正则挑的页 | 少了作者、组织、仓库；不读 LICENSE；GitHub Pages 站没找仓库 | 程序先取仓库 API、LICENSE、`package.json`、定价页、页脚 → LLM 判断七项和覆盖范围 → 程序逐字核对 quote | 程序 + LLM |
| 文案 | takeaway、手记（120–180 字）、三条导览、alt、简介、reasons | 只有 takeaway、简介中英 | 少了手记、导览、alt、reasons；只读首页文字，看不到图 | 编辑读卷宗、事实，并看三张通过的图 | LLM（看图） |
| 图鉴术语 | 可选，termId 要能在 manifest 里找到 | 无 | 可后补 | 二期 | LLM + 程序校验 |
| 独立复核 | 另一个 Agent 复核事实与截图 | 事实审查、文案审查 | 基本对齐 | 保留 | LLM |
| 发布闸门 | `npm run data` 校验 v3 JSON | 自己的闸门，记录格式是 v3 的子集 | 产出不是 VisLexicon 能直接用的格式 | 闸门直接调用 VisLexicon 的 v3 校验；产出就是 `approved-v3/<id>.json` | 程序 |

### 脚本比 LLM 合适的环节

这些交给程序更准、更快：

- 打开页面、等待静默、拒绝 Cookie、隐藏浮层；
- 识别舞台、裁切、补边、空白检测、感知哈希去重；
- sha256、尺寸、字节数；
- 从 GitHub API 取 SPDX 许可；
- quote 是否逐字出现在原文里；
- 文案里的数字能否在资料里找到；
- taxonomy 取值是否合法；
- v3 schema 校验。

### 必须用 LLM 的环节

需要"读懂"或"看懂"的判断：

- 站点理解和选页；
- 在几个候选舞台里认出哪个是组件本身；
- 分类和 facets；
- 事实的覆盖范围和冲突；
- 看图审查和风格；
- 编辑手记。

## 3. v2 策展线

```
候选层：规范化 + 健康预检（程序）→ 分流
① 去重（程序）
② 侦察员（程序）：建站点卷宗
③ 阅读员（LLM）：四问 + 拍摄单 + 事实线索
④ 分类员 ∥ 分类复核员（LLM，并行）→ 有分歧时仲裁
⑤ 编目员（LLM）：facets 12 轴
⑥ 首屏 / 目录（程序）  ⑦ 特写（Agent + 程序）  ⑧ 录屏（程序，只录动效站）
⑨ 图像处理（程序）→ ⑩ 截图审查（LLM 看图）
   与 ⑥–⑩ 并行：⑪ 事实（程序取资料 → LLM 判断）→ ⑫ 事实审查（LLM）
⑬ 风格（LLM 看图 + 程序否决）
⑭ 编辑（LLM 看图）→ ⑮ 文案审查（LLM）
⑯ 发布闸门（程序，VisLexicon v3 校验）→ 已发布（输出 v3 JSON + WebP）
```

**侦察员**做的事：

- 用 1 个浏览器页渲染首页，拿到全部可见文字，以及每个链接在导航、正文、侧栏还是页脚；
- 用 HTTP 并发取 `llms.txt`、`llms-full.txt`、`sitemap.xml`、`robots.txt`；
- 抓目录、关于、定价、许可页的标题和前段文字；
- 识别建站框架；
- 找到仓库后，调 GitHub API 取元数据。

浏览器只占约 8 秒，其余都是 HTTP。

**耗时估计（未实测）：**

| | 单站耗时 | 每站模型调用 |
|---|---|---|
| 现在 | 约 3 分钟 | 约 9 次 |
| v2 | 约 4–5 分钟 | 约 12 次 |

慢下来的部分主要是侦察员、阅读员和看图编辑。省下来的部分：特写不再盲试 6 页，事实和编目与拍照并行。

由于浏览器时间反而减少，每小时能处理的站数预计不降，但要以实测为准。

## 4. 环境层：让 Agent 在这里不容易出错

原则：Agent 只调用高层能力，拿到的是结构化结果；网络、代理、重试、缓存、分类报错由环境层统一处理。所有能力通过同一个能力服务暴露：Easy Workflow 内部工位直接调用，外部 Agent 通过 MCP / `easy_workflow_call` 调用。

1. **一个网络出口。**
   - 所有 HTTP 统一走一个客户端，自动使用系统代理（这台机器上 Node 必须设 `NODE_USE_ENV_PROXY=1`，否则会报自签名证书错误）。
   - 自带按主机限速、指数退避和内容缓存（带 TTL，同一页面同一轮只取一次）。
   - Node 请求失败（403、TLS、反爬）时，自动改用共享浏览器会话再取一次，并记录用的是哪条路。上一轮 Medium 的 403 就属于这种。
2. **报错直接告诉 Agent 下一步。** 每个失败都带固定的类别、已试过的方法和 `nextAction`，比如"证书过期：需要站长对这个主机明确放行；已试 HTTP 与浏览器"。Agent 不会拿到一段 stack trace 然后乱试。
3. **开跑前体检。** 新一轮开始前自动检查：
   - 代理和 DNS；
   - 模型接口（发一条极短请求）；
   - 浏览器能否启动、**后台页能否真的截出画面**（上一轮截图超时的 bug，这一步就能当场抓到）；
   - 磁盘空间、共享会话的登录状态。

   任何一项不通过就不开跑，而不是开跑后让 9 件货全部失败。
4. **自愈。**
   - 浏览器进程崩溃：自动重建页面池。
   - 模型 429 或额度用完：暂停这条线并通知，不把货标成失败。
   - 内存或磁盘不足：暂停领取新页面。
5. **系统 bug 一律修代码，并补回归。**
   - 每修一个 bug，就把触发它的真实站点做成测试夹具。
   - 每轮开始前，用 5 个固定站点跑一次"金丝雀"小样，发现环境漂移。
6. **数据位置固定。** 当时由不同入口启动 GUI 会使用不同的应用数据目录，造成工作区不一致。改为显式选择项目文件夹，并通过 `FACTORY_VAR` 或桌面项目配置指向同一目录；个人机器上的旧路径只在本地迁移记录里保存。

## 5. 候选层规范化（只对以后进来的候选，现有 8,684 条不动）

候选进入候选层时，一次性整理成统一记录：

- **原始观测**：原样保存（来源、发现时间、原始 URL、所在帖子或合集）。遵守 VisLexicon 的规则：原始命中数守恒，重复的写处置记录，不静默丢弃。
- **规范 URL**：
  - 主机名转小写，去掉 `utm_*`、`ref`、`fbclid`；
  - 保留决定页面内容的参数（Storybook 的 `path` / `id`、hash 路由）；
  - 跟随重定向，记下最终地址。
- **资源类型**：网站、代码仓库、npm 包、文档里的单页、社媒帖子、文件（DESIGN.md、PPT 等）。
- **仓库写法统一**：`git+https://`、`git@github.com:`、`.git` 后缀、`/tree/main/...` 都转成 `owner/name`（加上可选路径）。
- **实体键**：官网、文档、仓库、npm、旧域名归到同一个实体。合并必须有强信号（官网明确链接到这个仓库，或 `package.json` 的 homepage 指回官网），其余只记为候选对，等人或 Agent 裁定。
- **健康预检**（带检查时间缓存）：DNS、TLS 是否有效及到期日、HTTP 状态、是否登录墙、是否需要代理。不健康的不进产线，直接带标签放回候选库。

## 6. ROLE.md：外挂、通用、不依赖某个 Agent

- **ROLE.md 是唯一来源。** 现在每个 Agent 工位有两层提示：`stations/*.md`（英文）和 ROLE.md（中文）。合并成一份 ROLE.md，不再用脚本生成，每份手写。
- **注入由 Easy Workflow 完成，不改 Agent 内部。** 每次调用前，Easy Workflow 依次拼出：
  1. ROLE.md 全文；
  2. 这个工位已批准的"已知坑"；
  3. 输入输出契约；
  4. 本次任务的资料。
- **按 Agent 类型选注入方式：**
  - pi：放进 systemPrompt；
  - 闭源 CLI Agent（Claude Code、Codex CLI 等）：放进第一条消息，或用它们自带的附加系统提示参数；
  - 工具和提交：通过能力箱的 `env_help`、`env_call` 与 `submit`，外部工位使用受限 MCP 接口。

  这样换哪个 Agent，看到的身份、工具和提交方式都一样。
- **程序工位的 ROLE.md 只给人看。** 它写的行为必须由代码保证；其中提到的程序检查，会对应到测试用例上。
- 主调度"新建工位时学会写 ROLE.md"放到下一步，先审这 5 份样稿的风格。

## 8. 需要站长拍板

1. 基准要求"人写的中文描述"。v2 由 LLM 写编辑手记、独立审查，你在证据板抽查。这样是否可以接受，还是手记必须由人改过才能发布？
2. 证书过期的站：只有你明确放行某个主机时，才允许继续截图（Agent 自己永远不跳过证书校验）。这个口子要不要留？
3. 验收办法：拿 5 个 VisLexicon 已发布的站（建议 magic-ui、uiverse、laws-of-ux、carbon、lucide）用 v2 重跑，逐字段和现有记录比对，并记下耗时。
